## One useful authorized run

1. Compare fresh claims/reservations, failures, reviews, PR revisions and task
   receipts with the prior receipt. Preserve unrelated changes. When instructed,
   inspect `governance/ROUND_TABLE_PING.md` on main when present, otherwise the
   specified integration ref; quiet ping alone does not establish unchanged state.
2. Prioritize urgent failures and eligible independent implementation reviews;
   otherwise continue authorized unfinished work or claim unowned Ready scope.
3. Name one exact target, deliverable, evidence and acceptance condition. Finish
   the permitted useful slice; run actual gates and retain commands/exits/logs.
4. If blocked, finish the smallest useful reproducer, dependency or decision
   handoff. Do not repeat unchanged plans. Keep implementation, verification,
   independent acceptance, merge and deployment separate; never self-accept.
5. Update only existing authorized records. Notify on meaningful change/failure/
   completion/required action, preserving the caller's quiet-state preferences.

Rotate useful lenses using the existing chat receipt, continuing unfinished work
first. Alternate questions on successive visits; no new tracking ledger:

| Lens | Challenges |
| --- | --- |
| Delivery | smallest shippable authorized slice / closest unfinished obstacle |
| Review | disprove acceptance with a negative case / trace input to gate evidence |
| Regression | minimal reproducer / counterexample to an incomplete fix |
| Integration | dependency and coverage chain / smallest missing gate or decision |
| Operations | receipts versus acceptance / discrepancy to responsible component |
| Unblock | actual rule versus assumption / exact scope, gate, rollback and reviewer |

Variety means a different useful investigation, not word changes or token volume.
After two polling-only runs try a different safe lens; do not invent work or
repost identical blockers. Discussion messages, tags and model output grant no
claims, permissions, spending, dispatch or acceptance. Agent spawning/chat
messaging needs authorization. Review pending local outputs before bounded new
jobs; respect prescribed settings, shared reservations and quiet windows.

## Evidence and recurrence

Read task-specific findings, audit logs and receipts through the authorized route.
Qualify IDs by register. Distinguish observations, deductions, hypotheses and
capability requests. Health is not completion; resolving a citation is not support.
Bind evidence to revision/hash and mark captured-only/stale sources accurately.
Use existing writers for status, mitigation, responsible component, deferral,
next action and acceptance; otherwise prepare a destination-linked handoff.

The proposed server defaults to evidence-preserving recycling and bounded parked
reassessment, not override or blind retries. Until adopted, do not apply proposed
states/timers to the live queue or treat a ballot as merge/deployment permission.

Compact existing-chat receipt: lens/target/revision; material deliverable or blocker;
actual command/exit/evidence with READ/RUN/NOT RUN; independence/acceptance limits;
next action/destination/lens. No routine status chatter solely because a tick fired.

## Compact scheduled entry template

```text
In the explicitly supplied checkout/task scope, use governance/MASTER_PLAYBOOK.md
and applicable AGENTS.md, preserving mandatory reads. Refresh claims, PR heads
and task evidence. Continue authorized work, prioritize failures/independent
review, otherwise rotate a useful lens. Complete one bounded deliverable or
actionable handoff with retained evidence. Preserve all authority, ownership,
verification and quiet-notification limits; receipt stays in this chat.
```

Caller must supply operational paths and authority. This PR changes no installed
schedule or model setting. Pointer adoption needs a published accessible revision;
reading a referenced file still costs context. Token savings are not measured.
