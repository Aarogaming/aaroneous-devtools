The right model is not “Aaroneous generates work through a local agent.” It is:

The current system is upside down at the bottleneck: it has 731 retained proposals, 693 unreviewed. That makes more generation almost entirely low-value.

Best division of labor:

  • Aaroneous: exposes truthful, versioned evidence—component inventory, capability registry, test/gate results, failures, and bounded contracts.
  • Devtools: does deterministic work: select one goal, extract precise evidence, reject duplicates, enforce WIP limits, package an input, retain provenance, and show the reviewer only the next useful batch.
  • Local agent: performs bounded judgment that deterministic tooling cannot: explain a failure, compare 2–3 concrete approaches, draft a focused test/patch, or classify evidence against a rubric.
  • Human/cloud reviewer: decides whether a result becomes a queue candidate, receives feedback, or dies. Promotion stays separate.

The key change should be a “review-pull” pipeline:

  1. No new local-agent call unless there is available review capacity.
  2. One active result per work goal/evidence fingerprint; do not regenerate unchanged recurring audits.
  3. Every result must answer one decision: accept a finding, reject it, request revision, or archive it as no-action.
  4. Feedback changes the next prompt only when a reviewer gave actionable feedback.
  5. Use output metrics that reward progress: reviewed results, accepted findings, verified patches, and repeated-error rate—not generated jobs or tokens.

I would narrow local-agent work to four high-yield modes:

  • Evidence extraction for a specific claimed/review-ready problem.
  • Counterexample or test-fixture drafting for a stated invariant.
  • Two-to-three-option design comparison when a genuine decision is unresolved.
  • Focused patch drafting after a reviewer has already confirmed the defect.

I would suspend broad recurring architecture audits and generic “improve Aaroneous” jobs until the backlog is below a defined review cap. The immediate next project should be a bounded current-review batch generator that ranks the 693 unreviewed records by: confirmed defect severity, freshness of evidence, reviewer feedback, duplicate-pass suppression, and connection to an active roadmap item.

What I verified:

  • 297 current analysis jobs produced analysis-style proposals. That is expected; they were not supposed to implement code.
  • 46 current code-draft jobs produced results.
  • Only 11 of those 46 include a non-empty rust_draft.
  • 35 code-draft results contain no actual code, despite being labeled pending-owner-review rather than failed or incomplete.
  • A concrete positive example exists: FIX-C40-CONCURRENCE-PATH includes a Rust draft.
  • But that draft remains uncompiled, untested, and unverified—it is a proposal, not completed work.

So the central defect is not merely too much generation. The pipeline treats these materially different states as the same:

  • analysis produced;
  • code draft produced;
  • code draft omitted;
  • draft pre-proofed;
  • reviewer approved;
  • product change verified.

They all collapse into pending-owner-review.

The fix is to make output state truthful and mechanical:

  • A code-draft job without rust_draft must be needs-changes or failed, never reviewer-ready.
  • A non-empty draft should be structurally validated and pre-proofed before it enters the review queue.
  • analysis outputs should be routed to a decision queue, not mixed with patch review.
  • Review views should lead with: “actual draft present,” “pre-proof result,” “evidence freshness,” and “prior feedback incorporated.”
  • Only a reviewer verdict plus native Aaroneous verification may become “accepted” or “implemented.”

That turns the local agent from a prolific proposal generator into a source of reviewable work.
